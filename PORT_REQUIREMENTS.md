# xterm.js to Rust port

## User request and authority

Port source_repo/*, the supplied xterm.js 6.0.0 tree, into this repository in Rust. Preserve all APIs, contracts, features, and observable behavior, including browser and headless functionality and all addons. Support Windows, Linux, and macOS. Provide exhaustive practical unit, integration, differential, and end-to-end verification plus a usable Rust demonstration. Compare the original and port for speed, distributed artifact size, and lines of code. The user requested 45 swarm agents and instructed the swarm not to declare completion without proof.

Read AGENTS.md before working. Main adapted its quality bar for Rust and committed it in b8aa373 before launching this swarm. Do not change AGENTS.md. Do not overwrite unrelated pre-existing work. The initial untracked .gitignore, SWARM.md, and start-swarm.ps1 belong to the user. Never commit .pi/swarm credentials or runtime data. Temporary files go in tmp/. All bash calls require timeouts.

## Implementation

1. Establish a coherent Rust workspace with a documented edition, MSRV, features, build commands, and compatible licenses. Keep the platform-independent terminal engine separate from native adapters and browser/WASM integration. Coordinate shared interfaces early so parallel implementations integrate rather than becoming disconnected libraries.
2. Implement terminal parser state machines, handlers, buffers, cells, attributes, scrollback, reflow, Unicode, options, events, input/output, lifecycle, terminal APIs, and all other source behavior. Preserve streaming boundaries, JS UTF-16 indexing, numeric behavior, event ordering, error paths, callback/disposal semantics, proposed API gating, and option mutability.
3. Implement browser/WASM integration and the original DOM/WebGL rendering and browser interaction contracts. Preserve keyboard, mouse, selection, accessibility, links, clipboard, sizing, composition/IME, focus, themes, rendering and all addon behavior. A headless terminal alone is not completion. Minimal JS binding/DOM bootstrap is allowed but the original JS terminal engine must not execute the Rust implementation's logic.
4. Map JS APIs to callable Rust APIs and, where needed for browser contracts and original test reuse, compatible browser bindings. Explain language-specific naming or representations without silently dropping behavior. Do not substitute a different terminal crate and claim source equivalence without proving all contracts.
5. Preserve source attribution and licenses for code, fixtures, Unicode data, and dependencies. Keep implementation files within the quality bar, documenting cohesive generated-data exceptions.

## Reproducible speed, size, and LoC comparison

Create checked-in scripts and docs/comparison.md with raw machine-readable measurements. No assumed speedup or invented measurements. Use the same input bytes, dimensions, scrollback, Unicode configuration, operation count, result validation, and workload definitions for JS and Rust. Use optimized release Rust builds and the original's production JS build. Include ASCII throughput, Unicode/grapheme workloads, mixed ANSI parsing, scrollback, resizing/reflow, and addon workloads where applicable. Compare browser rendering only through equivalent browser harnesses. Warm up JS and the browser, use at least 10 measured repetitions per workload after warmup, report median and p95, input bytes/operations, units, ratios, process-startup inclusion, OS/CPU/toolchain, and timing method. Keep setup separate from steady-state timing; compare equivalent work and validate outputs before timing. Report missing measurements as blocked, not zero. Do not compare native parsing with browser rendering and label it a speedup.

For size, build original production browser/headless bundles and Rust release native artifacts and browser/WASM distributions. List exact paths and raw byte sizes. For web distributions also give gzip and Brotli bytes, listing the WASM module, binding JS, CSS, and mandatory supporting assets separately and as a total. Use the same compression settings. Identify optional addons and dependencies included in each distribution; report comparable core-only and matched-feature totals. Explain why native executable size is not directly comparable to JS download size. Record stripping, LTO, optimization, and relevant build flags.

For LoC, provide a single reproducible tool/method for both trees with separate production library, addon, binding/glue, generated code/data, tests, demos, and tooling totals. Report physical lines, nonblank lines, files, and preferably comment-stripped code lines with tool/version identified. Never mix comment-stripped SLOC with physical lines or silently omit generated data or JS glue from the port. Include all required production files regardless of language.
