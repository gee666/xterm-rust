# Streaming text decoders

`crates/xterm-core/src/input/text_decoder.rs` ports the read-only reference `source_repo/src/common/input/TextDecoder.ts`. It has no dependencies and no unsafe code. Copyright and MIT notices remain in both implementation and tests.

## API mapping

| Upstream | Rust | Contract |
| --- | --- | --- |
| `stringFromCodePoint(number)` | `string_from_code_point(u32) -> Vec<u16>` | JavaScript UTF-16 units, including lone surrogates and upstream truncation of out-of-range values |
| `utf32ToString(data, start, end)` | `utf32_to_string(&data[start..end]) -> Vec<u16>` | Rust slices select the range; the result retains JavaScript code-unit semantics |
| `StringToUtf32` | `StringToUtf32` | `new`, `clear`, `decode` |
| `Utf8ToUtf32` | `Utf8ToUtf32` | `new`, `clear`, `decode`, public `interim: [u8; 3]` |

Rust `decode` appends to a reusable caller-owned `Vec<u32>` and returns the number appended. The upstream writes from offset zero into an unchecked target typed array. This representation change avoids unchecked output bounds and lets callers reuse allocation. Callers that want replacement clear their vector first. Existing contents do not count toward the return value.

UTF-16 input is `&[u16]`, not `&str`. This is necessary to retain lone surrogates and chunk boundaries between surrogate halves. UTF-8 input is `&[u8]`. Neither decoder flushes on empty input. `clear` discards pending input. Invalid UTF-8 sequences disappear without replacement characters. U+FEFF disappears, except for the upstream UTF-16 rule where it follows an unpaired high surrogate and is emitted as that surrogate's second code unit.

The Rust implementation shares sequence assembly between fresh and pending UTF-8 prefixes instead of duplicating each encoding length. An overlong two-byte sequence's final continuation byte is consumed directly. Upstream retries it, then immediately discards it. This does not change output or pending state.

## Verification

Run from the repository root:

```sh
node scripts/text-decoder-oracle.mjs
cargo test -p xterm-core --test text_decoder
cargo test -p xterm-core --test text_decoder --release
cargo clippy -p xterm-core --test text_decoder -- -D warnings
rustfmt --edition 2021 --check crates/xterm-core/src/input/text_decoder.rs crates/xterm-core/tests/text_decoder.rs
```

Observed locally on native Windows x86_64 with Node v24.15.0 and Rust 1.85.1:

- Original assertions: 288 discovered, 288 executed, 288 passed, zero failed/skipped/unrun. `results/text-decoder/oracle.json` records individual test names and hashes of source and original tests.
- Rust: seven grouped test functions passed in debug and release. The groups cover original conversion assertions, both full-codepoint suites, all nine original multilingual samples, streaming cases and regressions, BOM/clear, and JS differential traces. Original codepoint batches remain assertions over each value, rather than one representative per batch. Rust also checks U+10FFFF, beyond the original exclusive bound.
- Conversion boundaries: 14 direct JavaScript vectors include BOM, lone surrogates, supplementary pairs, values beyond U+10FFFF and u32::MAX; Rust also checks empty and partial slices.
- Differential: 2107 persisted traces, including 1024 seeded random traces per decoder plus explicit boundary cases. The seed is `0xdec0de`. Expected per-chunk output comes directly from JavaScript. UTF-8 interim bytes are checked after every chunk, including empty chunks. Malformed sequences, lone surrogates, BOMs and split prefixes are included.
- Targeted Clippy and rustfmt checks passed. Initial Clippy component absence was resolved by workspace setup. A workspace-wide fmt check found other agents' in-progress files and is not claimed to pass here.

The three fixture files are generated by the oracle script. Ordinary runs verify exact committed fixture contents; use `--generate` only for deliberate regeneration. The TSV is a cohesive data file over 350 lines, not implementation code. Regenerate rather than hand-edit it. The script executes a temporary copy of the original synchronous test body under native Node TypeScript support. Only import locations and the chai strictEqual import change. It uses Node strictEqual with the same assertions and does not claim that the full upstream Mocha project ran.

This subsystem result does not prove terminal equivalence, browser behavior, or other operating systems. Native Linux/macOS and integration into a full terminal remain separate verification work.
