# LoC comparison acceptance contract

This is the detailed gate for task #49 and aggregate criterion #9. It measures source, not functional coverage or downloaded artifact size. All items require retained raw output and independent review.

## LOC1. Exact line and byte semantics

- Apply the identical UTF-8 physical-line and nonblank-line algorithm to original and Rust trees. Include comments. Do not describe these numbers as comment-stripped SLOC.
- Empty file counts zero. A final LF does not add a phantom line. Unterminated final content counts once. CRLF counts once; standalone CR is content. Unicode whitespace-only lines are blank.
- Report raw bytes separately from line counts. Do not normalize repository files, newlines or escape fixtures to obtain matching bytes.
- Test empty, blank-only, comments-only, LF, CRLF, standalone CR, missing final LF, tabs, Unicode whitespace, BOM-only, BOM-plus-LF and binary input boundaries.
- Known source/configuration that is not UTF-8 fails explicitly. Binary fixture assets remain inventoried by bytes rather than being decoded with replacement characters.

Evidence: `lineCounts`, Node unit tests and `results/loc/tests.txt`.

## LOC2. Complete source classification

- Inventory all admitted files, including uncounted assets, with relative path, extension, raw bytes and SHA-256. Aggregate counted files, physical/nonblank lines and bytes without double counting.
- Separate production library, addons, bindings/glue, generated code/data, mixed code/data, mixed code/tests, tests, textual test data, demonstrations, tooling and configuration. Inline Rust test-annotated files outside test-only paths get whole-file mixed-code-tests counts, not a claim of pure production/demo lines. Explicitly distinguish this annotation scan from parsed test-only line counts.
- All required Rust, JS/TS, CSS, HTML and shader/glue source is included. Recognize additional native source extensions in the checked-in rules. Fail on an unrecognized production extension instead of silently omitting it.
- Classify declarations as bindings, addon source separately from tests/configuration, and real user examples separately from differential adapters named oracle or trace. Structured JSON/YAML/TOML under test fixture directories is test-data, even with a dependency-lockfile basename. Ordinary test tsconfig files remain configuration.
- Verify per-category, per-purpose and per-extension totals sum to the same complete counted total. Include generated tests and production data; do not hide their size.

Evidence: `scripts/loc-rules.json`, `purpose`, manifest rows and classification tests.

## LOC3. Generated and mixed data accounting

- Generated status requires an explicit path override or a recognizable comment marker near the file start. A generator containing the words `Generated by` in a string is not itself generated output.
- Standalone generated code/tables and production textual data get separate totals. Generated test code retains purpose `tests` even when its category is generated-code-data.
- Keep mixed upstream Unicode implementation/data files explicitly identified. Whole-file physical counts cannot isolate their table bytes from handwritten logic, so label them mixed-code-data. Do not report zero upstream Unicode data or pretend all mixed lines are generated.
- Preserve a complete path-level audit trail. Any data extraction or classification override requires an explanation, not an undocumented count reduction.

Evidence: generated-marker, production-data and mixed-file unit tests; explicit overrides and mixed lists in the rules; generated JSON manifests.

## LOC4. Exclusions and scan boundaries

- Exclude version control, dependencies, local credentials/runtime, temporary files, build outputs and report outputs before traversal.
- Exclude original `out-esbuild-test` outputs at every depth, as well as core/addon build outputs. Rebuilding the original must not increase its source count.
- Do not count source_repo twice when traversing the port root. Do not count pre-existing user swarm launcher files as Rust-port tooling. Exclude the reserved port-root target path even if it is the coordinator-approved build junction; ordinary and reference-tree symlinks must still fail. Inventory generated distribution copies with bytes/hashes, but suppress duplicate line counts only after exact equality with an admitted counted canonical source; missing/divergent copies fail.
- Report the exact excluded paths and rules hash. Do not follow symlinks or directory junctions outside the root; require explicit review instead.
- Unit tests must include nested dependency/build output, source_repo under port, private runtime files, reporting directories and a symlink/junction boundary.

Evidence: exclusion and symlink tests, per-tree excluded arrays and rules hash.

## LOC5. Reproducibility and reference cross-check

- Use only a documented Node version and checked-in scripts/rules, without an external paid or platform-specific counting service.
- Stable input produces identical inventory hashes and counts. Sort paths without locale dependence and hash exactly the bytes counted.
- Record the source inventory hash and port inventory hash independently. A working-tree scan is not an atomic Git snapshot; record it as such and refresh after integration stabilizes.
- Recalculate the legacy source-extension subtotal and compare against docs/baseline/source-loc.json. Expected baseline is 396 files, 96,130 physical lines, 87,026 nonblank lines and 3,962,777 bytes. `--check-baseline` must fail on a mismatch.
- The broader classification includes configurations and textual fixtures omitted by that baseline. Explain both methods instead of presenting the new total as baseline drift.
- Provide copyable CLI commands, custom-root/output options and invalid-argument checks. Never invent a public reference revision from the local tree.

Evidence: fixture determinism tests, checked-in manifests, summary baseline cross-check and docs/loc.md.

## LOC6. Honest reporting and integration refresh

- Publish original-versus-current-port values for every category, including zero categories, physical/nonblank/file/byte totals, the rule/tool versions and raw JSON paths.
- Mark an incomplete implementation snapshot as partial. No ratio or smaller-line-count claim may imply equivalent functionality while features are absent.
- Explain that source bytes are not JS download, compressed WASM, native executable size or speed. Artifact and speed comparisons retain their separate gates.
- Link the LoC section from docs/comparison.md without overwriting the speed/size owner's work. Ensure README/final verification can name the reproduction command.
- A clean rerun after integration and independent classification/exclusion review are required. Reports may exceed 350 lines only because they are generated complete inventories, not oversized handwritten modules.

Evidence: docs/loc.md, docs/comparison.md link, raw results and independent task review. Changing implementation counts do not invalidate the counting method, but final claims must use a refreshed snapshot.
